# 9. 内置功能：元指令、记忆、总结、代写、选项、事件摘要、故事线、状态栏与行内批注

AP 内置了一批角色扮演和写作中常用的功能。它们的“机制”由 AP 负责：识别、解析、显示成卡片、保存数据；**说法**由你负责：功能叫什么、模型要怎样输出、什么时候启用。

## 结构：模型交回来的“附加物”

除了正文，模型还可以交回一些**结构**：选项、事件摘要、记忆更新……AP 把它们显示成消息顶部或下方的卡片，或者存进数据里。内置的结构有：

| 结构 | 用途 | 花瓣中的名字 |
| --- | --- | --- |
| 回复（reply） | 叙述者以自己的身份回应用户（元指令时） | `<Freesia_Reply>` |
| 记忆（memory） | 新增、替换或删除一条记忆 | `<Freesia_Memory>` |
| 总结（recap） | 完整的剧情总结，替代较早的聊天记录 | `<Freesia_Summary>` |
| 代写（impersonate） | 替用户写的下一条消息 | `<Freesia_Impersonate>` |
| 事件摘要（synopsis） | 本段的时间、地点、事件、概要 | `<synopsis>` |
| 选项（options） | 几条供用户选择的下一步输入 | `<options>` |
| 状态栏（status） | 故事日期（或第 N 天）、星期、时间、地点、天气，显示在消息顶部 | `<status>` |
| 行内批注（annotations） | 写在正文里、针对某段文字的批注 | `annotations`（用于“Freesia 的评论”） |
| 自定义（custom） | 任何你想要的块，可以带自己的卡片组件 | — |

在 `preset.yaml` 里，你为每个结构写好：

- **名字**：对话式下用的标签名（如 `Freesia_Reply`），指令式下用的字段名（如 `reply`）；
- **说明**：结构整体和每个子项的说明，指令式下模型会在 JSON Schema 里看到它们；
- **格式说明**：两种写法下各一份，比如对话式“用这样的标签包起来……”，指令式“填进 `options` 字段，每项包含 label 和 content……”。

然后，需要这个结构的模组在设定里声明一下：

```markdown
---
id: options
name: User Options
group: features
region: guidelines
order: 1100
when: '!meta.pure && gen.type != "impersonate"'
structures: [options]
---
## User Options

Generate several diverse options for {{ap::name::user}}'s next input to advance the story.

### Format

{{ap::structure::options}}
```

当这个模组生效时，AP 才会向模型“要”这个结构：指令式下 JSON Schema 里出现 `options` 字段，对话式下 AP 从输出中寻找 `<options>` 标签。`{{ap::structure::options}}` 会按当前写法换成对应的格式说明。关掉模组，这个功能就完全消失。

## 元指令：直接和叙述者说话

用户在输入里写 `@Freesia`（`@` + 叙述者的名字），后面的话就是给 Freesia 本人的**元指令**，而不是故事的一部分。

- `@Freesia 这段节奏太快了，下一轮慢一点`——从 `@Freesia` 到这一段结束都是元指令；
- `@Freesia{ … }`——用花括号明确框出元指令的范围，可以跨段落。

AP 分两种情况处理：

| 情况 | 例子 | AP 的处理 | 花瓣的模组 |
| --- | --- | --- | --- |
| **纯元指令**：输入里只有元指令 | `@Freesia 你觉得这个角色怎么样？` | 故事暂停；使用任务工作流；Freesia 思考后以回复卡片作答 | `meta-pure`（要求回复、可更新记忆） |
| **混合**：元指令夹在故事输入里 | `我推开门。@Freesia 这里写得紧张一点` | 照常推进故事，同时遵守元指令 | `meta-mixed`（用 `{{ap::input::meta}}` 列出这些指令） |

为了不污染故事：

- 之前轮次中的元指令会从聊天记录里去掉，纯元指令的那一轮整个不发给模型；
- 但最近几次元指令对话会以 `{{ap::recent_meta}}` 的形式保留（条数由用户在“写作”页设置），花瓣把它放在 `<recent_meta>` 中，让 Freesia 记得刚刚说过什么。

元指令的触发词可以改（默认是 `@` + 叙述者名字，用户改名后自动跟随）。

## 自动识别任务：总结与代写

纯元指令里，如果出现某些关键词，AP 可以把它认作特定的**任务**。花瓣用两条正则规则：

- 包含“总结、概括、梗概、summary、recap……” → 总结任务；
- 包含“代写、帮我写、替我回、impersonate……” → 代写任务。

识别结果可以在条件里使用（`meta.task == "summary"`），对应的模组只在这时出现。这些关键词规则（以及它们生效的前提）都由你在 `preset.yaml` 里定义；你也可以定义其他规则，在条件中用 `flags.<规则名>` 读取。

## 记忆

记忆是一组“标题 → 内容”的条目，分两种：

- **聊天记忆**：属于当前聊天，随消息删除、滑动（swipe）一起回滚；
- **全局记忆**：使用这个预设的所有聊天共享，适合长期偏好和禁忌。模型写入的条目跟随写入它的回复：删除、重新生成或滑走这条回复时撤销，滑回这个版本时恢复。

模型通过记忆结构提出“替换”（新增或整条覆盖）或“删除”操作，AP 执行并显示一张记忆卡片。用户可以在“记忆”页直接查看和编辑。

花瓣的做法：

- `context` 模组在聊天记录之后放入 `<memory>` 和 `<global_memory>`（用 `{{ap::memory::chat}}` / `{{ap::memory::global}}` 读出，没有记忆时不出现）；
- `memory` 模组在有元指令时说明记忆系统的规则：**只有用户明确要求时才更新**，标题要稳定，替换时要写完整内容；
- 元指令模组声明需要记忆结构。

## 剧情总结

总结（recap）是一段完整的剧情概要。保存后，**它覆盖的那部分聊天记录不再发送给模型**，以总结代替，能大幅节省 Token。花瓣：

- 用户说 `@Freesia 总结一下目前的剧情` → 识别为总结任务 → `summary` 模组要求 Freesia 把旧的总结和新的剧情合并成一份完整的新总结；
- `context` 模组把当前总结放在聊天记录之前的 `<story_recap>` 中。

用户可以在“记忆”页查看、修改总结。

## 代写

ST 的“代写”（Impersonate）按钮会被 AP 接管：点击后，AP 发送预设设定的代写元指令（花瓣是 `@Freesia Please ghostwrite my next reply.`；输入框里已有的文字会作为提示附在后面），模型在任务工作流中写出代写结构，结果显示为卡片，点一下即可填入输入框。花瓣的 `impersonate` 模组说明了如何模仿用户的语气和写法。

## 选项

选项是几条供用户选择的“下一步输入”，显示为可点击的卡片：点击填入输入框，按住 Ctrl / Shift 等键点击则直接发送。花瓣要求每轮给出四个方向不同的选项，每个有一个简短的标题。选项数量在结构设定里固定（花瓣是 4），指令式下 Schema 会强制这个数量。

## 事件摘要与节省 Token

事件摘要是每段故事结尾的一张小卡片：时间、地点、事件标题、简要经过。点一下展开概要；摘要写得不准时，点行尾的铅笔就能直接修改，保存后覆盖原摘要，之后的请求都使用修改后的内容。它本身方便用户回顾，更重要的是它会随历史一起发回给模型，有两种方式：

- **最近几条附带摘要**：很多角色卡的正文里没有精确时间，模型只能从先前的事件摘要推断“现在几点”。在结构上声明 `history`（`depth: 3`），最近 3 条助手回复保留原文，并在后面附上自己的摘要，格式由 `history.template` 决定。这与是否打开节省 Token 无关。任何结构都可以这样回传（如状态栏插在正文之前），还可以加条件，见 [历史回传](../reference/structures.md#历史回传)。
- **节省 Token**：用户在“配置”页打开“节省 Token”后，最近若干轮（默认 6 轮）保留原文，更早的助手回复用它的事件摘要代替，格式由 `tokenSaving.synopsisTemplate` 决定，花瓣是 `[时间 · 地点] 事件: 概要`。

节省 Token 时，更早的用户消息有三种处理方式，预设在 `tokenSaving.userInput` 中指定默认值，用户可在“配置”页修改：保留、截断（默认保留 2000 字符）或移除。花瓣默认移除——它的扩写模式会把用户输入写进正文，事件摘要里也已经有了，再发送原始输入只是重复。

```yaml
structures:
  synopsis:
    kind: synopsis
    history:
      depth: 3                # 最近 3 条回复附带摘要
      template: "<synopsis>…</synopsis>"
      # 可选：只在纯文本 / 预填充传输下回传（作为格式示例）
      when: 'transport in ["plaintext", "prefill"]'
tokenSaving:
  userInput: remove           # keep / truncate / remove
  synopsisTemplate: "[{{time}} · {{location}}] {{event}}: {{summary}}"
```

这些都是“滑动窗口”：每一轮都有一条较早的消息从原文变成摘要、或者去掉了回传的摘要，提示词在那里变了，服务商的提示词缓存也就从那里失效。“配置”页的**缓存优化**打开后，缓存还可能命中时，每条历史消息沿用上一次请求的渲染，只有新消息按规则渲染；缓存过期（默认 5 分钟）、换了模型、工具或历史之前的提示词变了，或者已经连续推迟了太多轮（AP 默认 6 轮），才一次性按规则刷新。预设可以在 `configurationDefaults.cache` 中调整默认值，花瓣把最大推迟轮次设为 8：

```yaml
configurationDefaults:
  cache: { maxDeferredTurns: 8 }   # enabled 默认 false，由用户打开
```

所以如果你的预设想支持节省 Token，就提供一个事件摘要模组，并让它默认打开。完整字段见 [structures.md](../reference/structures.md#synopsis) 与 [manifest.md](../reference/manifest.md#省-token-tokensaving)。

## 用户输入整形

后置指令常常要提到“用户这次说了什么”，但本次输入混在聊天记录里，没有一个可以引用的名字。**用户输入整形**是预设级的功能（用户没有开关），在清单里声明一次：

```yaml
# 包裹：聊天记录里的本次输入换成 <input>…</input>
inputShaping:
  mode: wrap
  template: "<input>\n{{content}}\n</input>"
```

```yaml
# 提取：本次输入离开聊天记录，由宏放到你想要的区域
inputShaping:
  mode: extract
```

提取时，用一个条目把它放回来，并用 `input.shaped` 判断这次有没有输入：

```markdown
<!-- @entry id=input region=input order=100 when="input.shaped" -->
<input>
{{ap::input::text}}
</input>
```

规则很简单：**聊天记录以用户消息结尾**时才整形——普通发送、重新生成、滑动都会；“继续”、`/trigger`、其他插件在助手消息之后发起的生成不会。世界书的深度 0 注入等插在输入之后的内容不影响判断。花瓣预设用的是提取：输入放在记忆与问题之间的 `input` 区域里（见[案例](13-petals-case-study.md#第二步划分区域)）。

用 `ap preview --input "……"` 可以看到整形后的样子。细节见[参考](../reference/manifest.md#用户输入整形-inputshaping)。

## 故事线

长篇角色扮演常常需要“岔出去写一段”：某个配角的回忆、另一条时间线、“如果当时选了另一条路”。**故事线**让用户在同一个聊天里写多条线，AP 负责把它们分开、排好，再交给模型。和用户输入整形一样，它是预设级的声明，但用户在配置页有一个总开关：

```yaml
# manifest/behavior.yaml
storylines: true          # 使用默认分隔
# 或者自定义每组之前的分隔（系统消息）
storylines:
  separator: "<!-- Start of Storyline {{storyline}} -->"
  mainSeparator: "<!-- Start of the main storyline -->"
```

用户怎么用：

- 在故事输入的末尾写 `#支线名称`，这条消息和之后的回复就属于这条支线；没有标签的消息属于主线。标签在显示和发送给模型时都会隐藏，只在编辑时可见；
- 名字以 `if` 开头的支线是 **if 线**（另一种可能）。主线和其他线都看得到普通支线的内容，但看不到 if 线的内容；是否为 if 线可以在故事线面板里切换；
- 每条助手消息按滑动（swipe）记录自己属于哪条线；用户改了标签，之后的回复要重新滑动才会换线；
- `#!新主线名称` 把某条支线设为新主线；如果旧主线还没有名字，AP 会弹窗请用户先起名。

AP 怎么排历史：在主线上，所有支线的内容挪到前面，主线在后；在支线上，其他线在前，当前支线放在最后。每组前面有一条系统消息作为分隔。**世界书和其他按深度插入的内容始终按“相对主线”的位置插入**——世界书通常是为主线故事写的。非当前的支线在有事件摘要时总是只保留事件摘要（并截断长输入），非当前的主线按节省 Token 的深度处理；每条线有各自的缓存状态，切换回来时缓存仍然有效。

**读取聊天也按故事线的顺序。** 自定义结构的 `::last` 和 `last.*`、聊天记忆、事件摘要、“最近的元指令”都按当前故事线重整后的顺序来读：切到支线时，状态栏等结构读到的是这条支线（或它之前的其他线）的上一条，而不是楼层上的上一条；当前线看不到的 if 线也不会被读到。

**支线轮次的变量。** 变量系统（MVU、酒馆助手的聊天 / 消息变量）只认楼层顺序，支线上的变化会被带回主线。因此配置页有一个开关“支线轮次不更新变量”（`storylines.freezeVariables`，默认开）：在主线以外的故事线上生成时，AP 丢弃 MVU 这一轮解析出的变量命令并恢复它的状态，并在这一轮结束后把酒馆助手的聊天变量和这一轮消息的变量还原为生成前的样子。AP 只通过 MVU 公开的事件和聊天数据完成这些，不调用酒馆助手的代码。角色卡、全局和脚本变量不受影响；MVU 的“额外模型解析”请求仍会发出，只是结果不生效。

预设要做的，是告诉模型“历史是怎么分组的”和“现在在写哪条线”。可用的条件和宏：

| 写法 | 意思 |
| --- | --- |
| `storyline.name` | 当前故事线名称（在主线上为主线名称，未命名时为空） |
| `storyline.main` | 当前是主线 |
| `storyline.if` | 当前是 if 线 |
| `storyline.new` | 当前故事线还没有消息（这一轮开始它） |
| `storyline.grouped` | 历史按故事线分组（可见的线不止一条，带分隔消息）；在主线上也可能为真 |
| `{{ap::storyline}}` / `{{ap::storyline::main}}` | 当前故事线名称 / 主线名称 |

推荐拆成两个条目：结构介绍放在历史区域，只在历史真的分组时出现；当前线的说明和操作指南放在输入区域、用户输入之前，离模型要写的内容最近。支线上的状态是独立的，最好明确告诉模型不要更新变量、写数据库或产生其他副作用：

```markdown
<!-- @entry id=storylines region=history order=50 when="storyline.grouped" -->
下面的历史按故事线分组，每组前有一条“Start of Storyline …”的分隔；各组不按故事时间排列。
主线是故事的主干；支线与主线发生在同一个世界里；名字以 if 开头的是 if 线，是另一种可能。

<!-- @entry id=storyline region=input order=30 when="!storyline.main" -->
<!-- @if storyline.if -->
这一轮写的是 if 线「{{ap::storyline}}」：一种与主线并行的可能，不会改变主线。
<!-- @else -->
这一轮写的是支线「{{ap::storyline}}」，它与主线发生在同一个世界里。
<!-- @end -->
只写这条线的内容。支线的状态是独立的：不要更新变量、写入数据库或产生其他副作用，即使设定要求这么做；只输出故事正文和这个流程要求的内容。
用 `ap preview --storyline 名称`（或再加 `--storyline-new`）可以检查支线上的提示词；`--storyline-grouped` 检查分组历史下的主线。故事线面板（消息顶部的小卡片或配置页按钮打开）列出所有故事线和它们的楼层，可以跳转、切换 if 线、设为主线。细节见[参考](../reference/meta-and-tasks.md#故事线)与[清单](../reference/manifest.md#故事线-storylines)。

## 行内批注

行内批注让叙述者在正文里“划一句、写一句”：模型写 `{==原文==}{>>批注<<}`，AP 把标记从正文中去掉，只保存批注本身。读者看到的是带虚线下划线的文字，悬停（手机上轻点）弹出批注气泡，署名为叙述者。

- 正文保持干净：消息里没有标记，关掉 AP 或换预设也不受影响；流式时标记不会闪现；
- 用户编辑正文后批注会自动跟随原文；找不到原文的批注保留但不显示（调试页可查）；
- 酒馆助手等前端界面若在同源 iframe 中显示了同样的文字，也会自动画上下划线；前端可以用 `data-ap-annotations="off"` 关闭，或用 `"manual"` 自己通过 API 绘制；
- 默认历史里只有干净正文；结构的 `history: N` 可把最近 N 条消息的批注重新放回历史，代价是 token。

批注最好**少而精**。建议把**语法**写在结构的 `formatPrompt` 里（与用途无关，可被不同模组复用），把**写什么、写多少、用谁的口吻**写在模组里。花瓣就是这样做的：结构 `annotations` 只说明标记语法；模组“Freesia 的评论”（默认关闭）让 Freesia 以自己的口吻在正文上留下至多三条评论，而且只在她本来就会回复时发送（开启“始终请求元回复”，或输入中含混合元指令）。语法与字段见 [结构参考](../reference/structures.md#annotations)。

## 状态栏

状态栏（`kind: status`）是一行显示在消息**顶部**的小卡片：日期（或“第 N 天”）、星期、时间、地点、天气。它最好在正文**之前**生成——模型先确定“现在是什么时候、在哪里”，再写正文，时间线更稳定：

```yaml
structures:
  status:
    kind: status
    order: { before: "@content" }     # 思考 → 状态栏 → 正文
```

请求它的模组里可以用 `{{ap::structure::status::last}}` 读出上一轮的状态，让模型在此基础上推进。卡片可以手动编辑，流式生成时就会显示。

## 顺序：结构可以插在阶段之间

默认情况下，结构排在正文之后。需要别的位置时，给结构写 `order`（或在工作流里写 `structures.order`），比如 `{ before: "@content" }`、`{ after: thinking }`。指令式传输中，再在清单里打开统一排序前缀：

```yaml
tools:
  orderPrefix: true          # 字段名变成 1_thinking、2_status、3_story、4_synopsis
  turn: { field: "{{stage}}" }
```

这样即使 API（如 Gemini）按字母顺序生成字段，顺序也不会乱。细节见 [字段名与顺序](../reference/structures.md#字段名与顺序)。

## 自定义结构

内置结构不够用时，可以声明**自定义结构**，比如一个心情块 `<mood>…</mood>`：

- 可以是一整段文字，也可以是“键 → 值”的形式；
- 可以显示成卡片，也可以隐藏（只保存数据）；
- 在提示词里用 `{{ap::structure::mood::last}}` 读出最近一次的值，让模型在上一轮状态的基础上更新；
- 还可以带**自己的卡片组件**：一段 EJS 模板（渲染成 HTML，适合简单界面），或一个 JavaScript 模块（可以用任意前端框架），放在消息顶部或底部。组件是代码，用户安装时会被询问是否“信任并启用”，未启用时不显示，之后可以在「配置 → 自定义 UI」里打开。写法见 [卡片](../reference/structures.md#卡片)。

## 设计建议

- **结构的名字要有辨识度**：花瓣给自己的结构加上 `Freesia_` 前缀，避免和角色卡里的标签撞名；
- **格式说明要具体**：给出完整示例，说明哪些部分可选、能不能重复、要不要转义；
- **记忆与总结要“谨慎”**：明确告诉模型只在被要求时更新，否则它可能每一轮都在改记忆；
- **代写和元指令时去掉故事专用的内容**：选项、事件摘要、文风在这些情况下用条件关掉。
